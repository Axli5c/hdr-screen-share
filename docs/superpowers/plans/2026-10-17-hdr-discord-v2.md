# HDR Screen Share v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Native execution in the current chat is preserved from the user's earlier choice. Review this saved plan with the user before implementation.

**Goal:** Компактное приложение с миниатюрой, независимым SDR-источником для Discord до 4K/60 и звуком приложений без микрофона, Discord и повторного локального воспроизведения.

**Architecture:** Подписанный VDD предоставляет отдельный виртуальный монитор; полноразмерное окно программы находится на нём. Нативный WASAPI-модуль в процессе программы захватывает непересекающиеся разрешённые деревья аудиопроцессов, смешивает PCM и выводит только в VB-CABLE. Python/PySide6 управляет ресурсами и показывает отдельный малый предпросмотр.

**Tech Stack:** Python 3.12 x64, PySide6 Essentials 6.12.0, hdrcapture 0.3.0, NumPy; C++17/MSVC v142 + WASAPI/COM для audio_bridge.dll; подписанный Virtual Display Driver 24.12.24 из релиза 25.5.2; VB-CABLE Pack45; PyInstaller onedir, pytest.

**Spec:** docs/superpowers/specs/2026-10-17-hdr-discord-v2-design.md

## Global Constraints

- Миниатюра — только предпросмотр, до 480×270 и 15 FPS. Размер миниатюры не ограничивает разрешение окна для Discord.
- Режим виртуального экрана — SDR, 60 Гц, размер соответствует источнику с ограничением 3840×2160, для портретного источника 2160×3840. Меньший источник не увеличивается.
- Окно «HDR Screen Share — Discord» размещается полностью на собственном виртуальном экране, не становится основным и не получает фокус.
- Не менять HDR, разрешение и основной физический монитор; не отключать чужие виртуальные мониторы и не восстанавливать поверх новых изменений пользователя.
- Физические устройства записи не открывать; обычную настройку микрофона голосового чата Discord не изменять.
- Исключить настольный Discord/PTB/Canary, его дочерние процессы и собственный процесс/детей; не дублировать захват одного дерева.
- Внутреннее смешивание — stereo float32, 48 kHz. Выход только в выбранный playback endpoint VB-CABLE внутри того же процесса, что окно Discord. Не менять системные устройства по умолчанию.
- Обычный нефильтрованный системный loopback и подмена микрофона Discord кабелем не являются допустимыми обходными путями.
- Установка — только после конкретного проверенного действия с повышением прав. Не включать test signing, не отключать Secure Boot, не импортировать самоподписанные корневые сертификаты. Перезагрузку не выполнять автоматически.
- VDD ZIP SHA-256 F93E7CE3D640C83C419B1B72D2C83B2D8E34D83E8B7BA11F3328A40D2DA82FA4; VB-CABLE ZIP SHA-256 B950E39F01AF1D04EA623C8F6D8EB9B6EA5C477C637295FABF20631C85116BFB. Перед установкой повторно проверить подписи CAT/DLL/SYS/EXE и соответствие каталога INF.
- Защищённые/недоступные потоки не обходить. При невозможности безопасной фильтрации звук заглушается с явной ошибкой.
- Приёмка 4K/60: не менее 59 новых представленных кадров/с в среднем за 60 секунд после прогрева, без неограниченной очереди. Целевое рассогласование A/V ≤80 мс, без дрейфа за 10 минут; результаты измерять.
- Реальную трансляцию людям не включать без указания пользователя. Отсутствие проверки вторым клиентом — явный незакрытый критерий, не доказательство готовности.

## Review Focus

1. Смешанный процессный граф, повторный PID и перезапуск Discord: ни один запрещённый процесс не должен попасть в разрешённый захват; при сомнении звук отключён.
2. Чужой VDD или изменение топологии: очистка не должна отключить чужой экран или переместить полноразмерное окно на физический монитор.
3. Несовпадение endpoint ID, потеря VB-CABLE или смена наушников: нельзя переключать релейный звук в физические колонки или дублировать его локально.
4. Медленный предпросмотр, сворачивание и переполнение аудиобуфера: полный вывод независим от миниатюры, память и A/V-задержка не растут.
5. Discord видит окно, но не получает его звук с VB-CABLE: наличие сигнала на кабеле не считается завершением полного маршрута.

### Task 2: Отфильтрованный звук и проверка доставки в Discord

**Consumes:** готовый playback endpoint VB-CABLE из Task 1, текущий PID программы и список render-сессий/процессов Windows.
**Produces:** `select_capture_roots(processes: list[ProcessIdentity], audio_pids: set[int], own_pid: int) -> list[ProcessIdentity]`, где `ProcessIdentity(pid: int, parent_pid: int, created_at: int, image_name: str)`; ошибка безопасного выбора — `AudioPolicyError`. `AudioRelay(endpoint_id: str)` с `start()`, `stop()`, `stats()`; C ABI нативного модуля описан ниже.

**C ABI:** `ab_open(const wchar_t* endpoint_id, AbHandle* out)`; `ab_list_processes(AbProcessInfo* buffer, uint32_t capacity, uint32_t* count)`; `ab_set_sources(AbHandle, const AbProcessInfo* roots, uint32_t count)`; `ab_get_stats(AbHandle, AbStats* out)`; `ab_stop(AbHandle)`. Коды HRESULT/ошибок возвращаются через ABI, исключения C++ не выходят в Python. `AbProcessInfo`: PID, parent PID, время создания и имя образа UTF-16. `AbStats`: число выходных кадров, заполнение очереди в кадрах, переполнения и последний HRESULT.

## Самопроверка плана

Все части связаны в один последовательный путь: устройства нужны для диагностического аудиомаршрута, маршрут проверяется до переработки интерфейса, упаковка следует за работающими компонентами. Пять Review Focus покрыты конкретными тестами или явно ручной end-to-end приёмкой. Две возможности остаются экспериментальными результатами, а не принятыми на веру фактами: управление конкретным подписанным VDD без затрагивания чужих дисплеев и получение звука VB-CABLE самим Discord. Их неуспех останавливает зависимые этапы.
