# HDR Screen Share — минимальная версия

## Цель и согласованный сценарий

Пользователь запускает небольшую программу, сохраняет HDR на своём мониторе и выбирает окно программы в Discord. Зрители получают SDR-картинку без пересвеченных светлых областей. Нужны игры и рабочий стол; для первой версии оба сценария покрывает захват целого монитора. Пользователь согласился выбирать отдельное окно вместо обычного источника «Экран» в Discord.

## Интерфейс

- Небольшое окно управления: выбор исходного монитора, выбор второго монитора для окна-копии, «Запустить / Остановить», понятный статус.
- В списке показаны все подключённые мониторы: имя, физическое разрешение и статус «HDR включён», «SDR» или «HDR неизвестен». Определять именно активный HDR, а не только способность монитора поддерживать HDR.
- По умолчанию выбран основной монитор с включённым HDR; если основной монитор в SDR, выбран первый монитор с включённым HDR. Если HDR-мониторов нет, выбрать основной и явно показать SDR-режим без повторного tone mapping. Захват выбранного источника запускается автоматически.
- Пользователь может выбрать другой HDR-монитор для преобразования; перед переключением завершить предыдущую сессию. Обрабатывать только выбранный монитор, остальные не изменять.
- Отдельное окно вывода с постоянным названием «HDR Screen Share — Discord» содержит только изображение, без элементов управления.
- Вывод в исходном разрешении до 4K UHD (3840×2160) с сохранением пропорций, целевая частота 60 кадров/с. Источник меньшего размера не увеличивать; большего размера уменьшать до границ 3840×2160. Для повёрнутого монитора границы 2160×3840. Размеры вычислять в физических пикселях независимо от масштабирования Windows.
- Проверка 4K/60 относится к захвату, преобразованию и окну вывода программы. Доступное качество и частота трансляции внутри Discord проверяются отдельно; программа не изменяет его ограничения.
- HDR и параметры Discord программа не изменяет.
- Вывод должен полностью помещаться на втором мониторе. Если его физическое разрешение меньше исходного, размер уменьшается с сохранением пропорций и с явным уведомлением; полноценный вывод 4K требует подходящего второго монитора. Это ограничение согласованного способа вывода.

## Технический подход

Приложение Python для Windows x64. Пользователь выбрал Python вместо предложенного ранее C++. Целевая среда разработки — Python 3.12; совместимость конкретных бинарных пакетов проверяется перед закреплением версий.

- PySide6: окно управления, перечисление экранов и отдельное окно вывода. Изображение отображается с сохранением пропорций; SDR-вывод Qt на HDR-дисплее требует проверки цвета через Discord.
- hdrcapture: непрерывный захват Windows.Graphics.Capture в режиме auto. По документации проекта, HDR преобразуется в SDR на GPU, SDR захватывается без дополнительного tone mapping. Нельзя использовать режим sdr для исправления HDR: он принудительно переводит захват в восемь бит с потерей светлых участков.
- NumPy: представление готового BGRA-кадра для передачи в QImage. Объект изображения должен владеть данными либо сохранять буфер до завершения отрисовки.
- PyInstaller: упаковка в переносимую папку с exe и зависимостями. Для запуска упакованного приложения отдельно устанавливать Python не потребуется; размер и комплектность проверяются после сборки.

Захват создаётся, используется и закрывается в одном рабочем потоке: hdrcapture документирует привязку к создающему потоку. GUI остаётся в главном потоке Qt. Передавать только последний доступный кадр через ограниченный буфер, без накопления очереди; закрытие приложения ожидает остановки рабочего потока. Номера экранов Qt и hdrcapture сопоставляются явно; нельзя считать их порядок одинаковым. При старте выполняется проверка доступности backend и устройств.

Преобразование HDR выполняется нативной частью hdrcapture, но готовые BGRA-кадры проходят через память CPU к Qt. Полностью GPU-конвейер в первой версии не обещается. Необходимо измерить нагрузку, задержку и частоту кадров именно при 3840×2160/60. Один BGRA-кадр 4K занимает около 33 МБ; однократная передача 60 кадров/с составляет около 2 ГБ/с, поэтому дополнительные копии ограничивать. Перерисовки одного и того же кадра не считать новыми захваченными кадрами. Если конвейер Python/Qt не достигает 4K/60, сообщить измеренный результат и пересогласовать способ передачи кадров; не подменять требование молчаливым уменьшением до 1080p. Первичная проверка библиотеки включает наличие совместимого Windows wheel, лицензию, API и качество смешанных SDR/HDR-сцен. Если библиотека не проходит проверку, показать причину и пересогласовать backend, а не незаметно переходить к обычному захвату с засветами.

## Вывод без рекурсивного захвата — уточнение после проверки

Первоначальный способ с окном за пределами рабочего стола проверен и отвергнут: Qt не перерисовывает полностью невидимое окно, а захват частично видимого окна не сохраняет внеэкранные пиксели. Пользователь явно согласился использовать второй монитор. Окно-копия без рамки размещается внутри второго монитора, отличного от источника захвата. Монитор вывода выбирается отдельно, автоматически предлагается первый отличный от источника. При смене источника нельзя оставить вывод на том же мониторе. При одном подключённом мониторе показывать понятную ошибку, а не запускать рекурсивный захват. Окно можно перекрывать другими окнами, но нельзя сворачивать. Нельзя применять к окну вывода WDA_EXCLUDEFROMCAPTURE: это помешает и захвату Discord. Работа при перекрытии другими окнами и фактический выбор окна Discord проверяются отдельно.

## Границы первой версии

Без виртуального монитора, драйвера, OBS, изменения клиента Discord, внедрения в игры и отдельного захвата звука. Звук не был согласован; первая версия решает только задачу изображения и не обещает звук игры при трансляции окна программы. Захват монитора рассчитан прежде всего на игры в безрамочном режиме; совместимость эксклюзивного полноэкранного режима проверяется отдельно, универсальная поддержка не заявляется.

## Ошибки и жизненный цикл

При отсутствии поддержки захвата, ошибке GPU, отключении монитора или прекращении кадров показывать понятный статус и позволять перезапуск. При закрытии освобождать сессию, обработчики событий и GPU-ресурсы. Изменение разрешения монитора пересоздаёт нужные поверхности; вывод сохраняет пропорции.

## Проверка готовности

1. Запуск приложения на Python и упакованного x64-приложения с комплектными зависимостями.
2. Проверка преобразования: чёрный, SDR-белый, яркие HDR-значения, нейтральная серая шкала, отсутствие NaN и сохранение различий ярких участков.
3. Ручная проверка на HDR-мониторе: рабочий стол и HDR-игра, остановка и повторный запуск, смена разрешения. Проверить выбор каждого из двух HDR-мониторов и смешанную пару HDR/SDR; выбор не должен зависеть от порядка экранов Qt.
4. Discord видит окно вывода; второй клиент получает движущуюся SDR-картинку без зеркального повторения и засветов.
5. Измерение частоты кадров и нагрузки на движущемся источнике 3840×2160 при 60 Гц или выше в течение 60 секунд после прогрева: отдельно захваченные уникальные кадры и представленные уникальные кадры, пропуски и задержка. Для приёмки 4K/60 средняя частота новых представленных кадров не ниже 59 кадров/с без накопления очереди; единичные задержки фиксировать. Проверить портретный монитор и масштабирование Windows 150%. Если нет доступа к HDR/4K-оборудованию или второму клиенту, эти проверки явно остаются невыполненными; поддержку 4K/60 не объявлять подтверждённой.

## Состояние среды

Python 3.12.14 и зависимости установлены в локальную .venv. Готовый wheel hdrcapture 0.3.0 загружен из GitHub Releases с проверкой SHA-256; системные MSVC/Rust не понадобились. Реальный HDR→SDR-захват проверен на основном мониторе 2560×1440, второй монитор также 2560×1440 и работает в SDR. Актуальная проверка сборки, частоты и ограничений описана в docs/verification.md.
